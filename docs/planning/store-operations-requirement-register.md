# Store Operations Requirement Register — SO-01

**Project:** RetailsOps — KDPS first deployment\
**Discussion and source review:** 29 September 2026\
**Authority:** The [main PRD](../prd.md) governs shared architecture, controls and release obligations; the [store PRD](../store-operations-prd.md) defines the immediate store feature scope. The [delivery roadmap](store-operations-delivery-roadmap.md) assigns work but does not approve a policy or activate a feature.

## Reading this register

The `ST-` table below has one accountable SO item for each of the 65 store requirements. A dependency or later P3/P4 portion does not create a second owner. The `R-` table classifies all 166 main-PRD requirements: **Store** means the requirement applies to the store milestone; **Split** names the part needed now and the part retained for SO-24; **SO-24** means the requirement remains in the later full-ERP commitment. Neither classification nor phase is an acceptance claim. Main-PRD owners, priorities and scope statuses are inherited from the metadata in each §7 subsection.

Four separate facts must be recorded: **code exists**, **behaviour verified**, **policy approved**, and **activated for the pilot**. Source inspection supports the first fact only. Where the register says *unverified*, no requirement-level acceptance result was established by SO-01. All real-store activations await their own gate decisions and SO-21 release evidence. The local startup/login evidence in SO-00 and synthetic fixtures do not establish real-store workflow acceptance.

The completion checks describe the results later delivery items must demonstrate, including applicable refusal, retry, offline, permission and reconciliation cases. A path in an evidence cell identifies implementation to inspect; it does not certify that the behaviour passes.
