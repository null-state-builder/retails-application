The negative probes also confirmed relevant failures: TypeScript rejects an invalid assignment; ESLint rejects explicit `any`; Prettier rejects a style violation; Vitest rejects empty test discovery; asset validation rejects a missing icon; and `api:check` rejects stale generated output. The launcher check confirms an inherited `COMPOSE_PROJECT_NAME=kdps-local` still resolves to the pinned proof project and a nonexistent proof project is refused. [`backend/tests/`](../../backend/tests/) covers accepted and refused money inputs, login/session denial and success, real persistence, rollback, restricted-role RLS and tenant isolation. [`frontend/src/pwa/config.test.ts`](../../frontend/src/pwa/config.test.ts) checks that service-worker navigation caching excludes API responses.

Current non-failing diagnostics are 18 ESLint React-hook or stale-disable warnings, one Django test warning for an absent local `staticfiles` directory, and Vite's large-chunk warning. These are visible in the check output; no warning was suppressed to obtain the pass.

The manual Linux runner used frozen installs directly before `npm run verify`. It did not run `npm run setup`, because that command also starts the local-development Compose project and this runner shared a Docker host with the existing demo project. The hosted workflow subsequently passed setup on its own isolated runner. The manual Linux proof stack used the pinned checkout-specific project and was removed with its disposable volume after the pass.

The first hosted run ([36547794801](https://github.com/null-state-builder/retails-application/actions/runs/36547794801)) failed before setup because the workflow requested nonexistent `astral-sh/setup-uv@v9`. Commit `0e1bae1` pinned the published `v7` action; the following hosted run passed every required step. This failure and repair changed only the workflow action version, not application behaviour or check strictness.

## Acceptance boundary

The committed-code clean Mac checkout passed setup and complete verification twice without changing tracked files. The same committed aggregate verifier passed in a disposable Linux runner after frozen installs, and hosted GitHub Actions passed clean setup, complete verification and tracked-file checks. SO-02 is accepted as the engineering baseline on this evidence. Store-device coverage, business-workflow acceptance and real-store activation remain with their later SO owners.
