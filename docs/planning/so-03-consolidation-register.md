# SO-03 consolidation and retirement register

**Inventory date:** 30 September 2026. **State:** working register; a named target and owner is a delivery obligation, not proof that migration or retirement has happened. The [machine-readable inventory](so-03-consolidation-inventory.json) discovers mounted API methods, commands, middleware, migrations, models, maintained modules, routed screens, navigation, bookmarks and frontend API callsites. Its [checker](../../scripts/check_so03_consolidation.py) detects added or removed surfaces and assigns one primary retirement owner to each. The access-cutover and workflow-retirement tables below, plus the [dependency map](so-03-dependency-map.md), are generated from that inventory. The [requirement register](store-operations-requirement-register.md) supplies requirement ownership. Static import and callsite discovery is not complete runtime tracing; each owner must attach endpoint-level tests and data reconciliation before removing its old path.

A target workflow owns all new writes after its cutover. Historical records, approval evidence, document numbers and links remain readable through the target until retention permits physical removal. A redirect or hidden menu item does not retire an API, service, model or screen. No bridge may grant authority after SO-03 cutover.

Inventory lifecycle labels describe the replacement decision, not acceptance: `canonical` is the retained target subject to its owner's tests; `temporary_supported_legacy` has a known or plausible current consumer and must stay protected until replacement proof; `historical_read_only` preserves evidence without an accepted write path; `retirement_candidate` is proposed for removal only after caller and data proof; and `unresolved` has a named owner and gate. A temporary API with no statically linked frontend callsite also carries a `consumer_trace` gate. Static discovery cannot prove that a runtime caller does not exist.
